# Техническое задание: Автономный фоновый сервис управления подсветкой клавиатуры AJAZZ при отключении экранов

## 1. Цель проекта
Разработать легковесную автономную фоновую утилиту на **Rust** для Windows, работающую без графического интерфейса и без консольного окна. 

**Основная задача:** 
- Автоматически выключать RGB-подсветку клавиатуры, когда изображение на всех экранах пропадает: мониторы уходят в энергосбережение по таймауту Windows или отключаются аппаратно.
- Автоматически восстанавливать прежний вид подсветки, когда экран снова включается.
- **Блокировка сеанса (`Win + L`) намеренно не гасит подсветку.** Экран ввода пароля при заблокированном сеансе должен оставаться освещённым: утром в тёмной комнате подсветка нужна, чтобы ввести пароль. Клавиатура гаснет только вместе с изображением на экране.

---

## 2. Требования к процессу и ресурсам
1. **Без интерфейса**: флаг компилятора `#![windows_subsystem = "windows"]` (приложение запускается как фоновый процесс без появления окна консоли `cmd`).
2. **0% CPU в простое**: запрещены таймеры с опросом в цикле и `busy-wait`. Приложение ждёт событий ОС через блокирующий цикл сообщений Win32 `GetMessageW`. Единственное исключение — опрос DDC/CI раз в 10 секунд (раздел 4.3), без которого невозможно заметить монитор, выключенный кнопкой; его замеренная стоимость нулевая в установившемся режиме.
3. **Потребление памяти**: минимальное. Достигнуто: рабочий набор ~1.9 МБ, приватная память ~2.4 МБ (раздел 9).
4. **Одиночный инстанс (Single Instance)**: использование именованного Win32 мьютекса (например, `CreateMutexW(..., "AK820_DisplayPowerWatcher_Mutex")`), чтобы нельзя было запустить две копии одновременно.
5. **Конфигурация**: все настройки (VID/PID, режим, яркость, скорость, цвет) задаются константами в коде. Внешний файл конфигурации не используется, зависимость для разбора TOML не требуется.
6. **Логирование**: программа пишет журнал в текстовый файл рядом с исполняемым файлом (например, `ak820-display-watcher.log`). В журнал записываются: запуск и остановка, подключение и отключение клавиатуры, смена флагов состояния, отправка команд выключения и восстановления, ошибки HID. Файл дописывается; ротация не требуется, но размер журнала не должен расти без ограничений (рекомендуется ограничить размер или очищать при запуске).

## 3. Целевое оборудование и HID-протокол

### 3.1. Идентификаторы устройства (AJAZZ AK820 Wired RGB)
- **Vendor ID (VID)**: `0x320F`
- **Product ID (PID)**: `0x505B`
- **Интерфейс**: вендорский HID-интерфейс (Usage Page `0xFF1C`, Usage `0x0092`, `interface_number == 1`).

*Поддержка AK820 Pro (VID `0x0C45`, PID `0x8009` / `0x800A`) в данной версии не реализуется и не тестируется.*

### 3.2. Формат пакетов протокола EVision (64 байта, Report ID внутри)
Пакет передаётся через `HidDevice::write` целиком, вместе с report ID. Длина — 64 байта, а не 65: отдельного байта Report ID перед телом нет.

Структура пакета:
- Байт 0: `0x04` (Report ID)
- Байт 1: младший байт 16-битной суммы
- Байт 2: старший байт 16-битной суммы
- Байт 3: `command` (код команды)
- Байт 4: `size` (длина полезной нагрузки)
- Байт 5: младший байт `offset`
- Байт 6: старший байт `offset`
- Байт 7: `0x00` (байт состояния в ответе клавиатуры)
- Байты 8..63: полезная нагрузка (до 56 байт)

> **Расчёт контрольной суммы**: 16-битная сумма всех байтов с 3 по 63 включительно, записанная little-endian в байты 1–2. Байты 0, 1 и 2 в сумму не входят.

### 3.3. Команды управления подсветкой
Коды команд: `BEGIN` = `0x01`, `END` = `0x02`, `READ_CONFIG` = `0x05`, `WRITE_CONFIG` = `0x06`.

Блок конфигурации — 29 байт. Значимые поля:
- байт 1: режим подсветки (`Static` = `0x06`, `Colourful` = `0x02`, `Off` = `0x18`)
- байт 2: яркость `0x00`..`0x04` (**`0x00` — подсветка выключена**)
- байт 3: скорость
- байт 4: направление
- байт 5: радуга (`0x01` / `0x00`)
- байты 6..8: цвет RGB

1. **Выключение подсветки**:
   Чтение текущего конфига (`READ_CONFIG`), сохранение его в памяти, установка байта 2 в `0x00` и запись обратно. Режим, цвет и скорость при этом не меняются — гасится только яркость.
2. **Восстановление подсветки**:
   Обратная запись сохранённого 29-байтного конфига. Прежний вид подсветки восстанавливается в точности, включая режим и цвет.
   Если конфиг не был снят (например, клавиатура была недоступна при выключении), выполняется чтение текущего конфига и установка яркости в `0x04`.

Порядок записи конфига:
1. `BEGIN` (`0x01`)
2. `WRITE_CONFIG` (`0x06`) — 29 байт одним пакетом
3. пауза 10 мс
4. `END` (`0x02`)

Каждый пакет подтверждается ответом клавиатуры: после `write` выполняется `read_timeout` с таймаутом 1000 мс. Байт 7 ответа, равный `0xFF` или `0xFE`, означает отказ.

### 3.4. Оптимизация работы с HID
- **Постоянное соединение**: дескриптор `hidapi::HidDevice` открывается один раз и удерживается в памяти. Пересоздавать `HidApi` на каждое событие нельзя.
- **Замеренная стоимость перечисления**: `HidApi::new()` на этой машине занимает **~10 140 мс**, открытие устройства — **4 мс**. Поэтому подключение выполняется заранее, при старте сервиса, а не в момент блокировки, иначе команда безнадёжно опаздывает.
- **Отдельный поток**: вся работа с HID выполняется в рабочем потоке, связанном с потоком сообщений через канал `mpsc`. Блокирующие вызовы hidapi не останавливают очередь системных сообщений.
- **Склейка событий**: если поток был занят и события накопились, применяется только последнее состояние (`try_recv` в цикле). Так подсветка не мигает серией устаревших команд.
- **Обработка разрыва**: если отправка вернула ошибку (клавиатуру отключили из USB), дескриптор сбрасывается, а подключение повторяется при следующей команде. Таймер не используется, требование 0% CPU сохраняется.
- **Отсутствие клавиатуры при старте**: сервис продолжает отслеживать события и подключается при первой команде.
- **Остановка сервиса**: при выходе, если подсветка была погашена, она возвращается.

## 4. Архитектура отслеживания событий Windows (Win32)

### 4.1. Скрытое окно сообщений
Для получения системных уведомлений в фоновом потоке создаётся нативное **message-only окно** (`HWND_MESSAGE`):
- `CreateWindowExW(..., HWND_MESSAGE, ...)`
- **Критично:** использовать именно `HWND_MESSAGE`, а не `WS_OVERLAPPED`. Обычное невидимое окно без родителя заставляет Windows непрерывно слать невалидированные сообщения `WM_PAINT`, что вызывает 100% нагрузку на одно ядро процессора. `HWND_MESSAGE` не участвует в отрисовке и гарантирует **0.00% CPU**.

### 4.2. Регистрация уведомлений
На созданный `HWND` регистрируются:
1. **Power Setting Notifications** (`user32::RegisterPowerSettingNotification`):
   - `GUID_CONSOLE_DISPLAY_STATE` = `{6fe69556-704a-47a0-8f24-c28d936fda47}` (0 = Off, 1 = On, 2 = Dimmed).
   - `GUID_MONITOR_POWER_ON` = `{02731015-4510-4526-99e6-e5a17ebd1aea}` (0 = Off, 1 = On).
   - `GUID_SESSION_DISPLAY_STATUS` = `{2b84c20e-ad23-4ddf-93db-05ffbd7efca5}` (0 = Off, 1 = On, 2 = Dimmed).
2. **Session Notifications** (`wtsapi32::WTSRegisterSessionNotification`):
   - Флаг: `NOTIFY_FOR_THIS_SESSION`.
   - Ловит блокировку экрана (`Win + L`) и разблокировку. Используется только для записей в журнале: подсветку блокировка не гасит (см. раздел 5).
3. **Сообщения топологии дисплеев**:
   - `WM_DISPLAYCHANGE` — отправляется при смене конфигурации мониторов (включая отключение DisplayPort монитора физической кнопкой) и при переключении системных десктопов.
4. **Сообщения сна системы**:
   - `WM_POWERBROADCAST` с `PBT_APMSUSPEND` и `PBT_APMRESUMEAUTOMATIC`.

### 4.3. Монитор, выключенный кнопкой: опрос DDC/CI
Проверено на реальном мониторе: при выключении **физической кнопкой** Windows не присылает **ничего** — ни `WM_DISPLAYCHANGE`, ни события питания. Линия остаётся «подключённой», `SM_CMONITORS` не меняется, монитор по-прежнему числится attached. Событийного пути для этого случая не существует.

Единственный признак — монитор перестаёт отвечать на DDC/CI. Реализация:

- Раз в **10 секунд** отдельный поток запрашивает VCP-код `0xD6` (состояние питания) у физических мониторов через `GetPhysicalMonitorsFromHMONITOR` + `GetVCPFeatureAndVCPFeatureReply` (`dxva2.dll`).
- Пока монитор включён, он возвращает `1`, ответ занимает ~55 мс.
- После нажатия кнопки запрос не проходит.

**Защита от ложных срабатываний.** DDC/CI сбоит и на исправном мониторе: в замере одиночные отказы появлялись в 6 случаях из 45 секунд. Поэтому одного отказа недостаточно — выполняется до 4 попыток с паузой 250 мс, и только если все подряд не прошли, монитор считается выключенным. Повторы стоят дёшево, потому что случаются только при подозрении.

**Стоимость.** Замер на реальной системе: за 115 секунд работы, включая 90 секунд с выключенным монитором и опросом каждые 10 секунд, процесс израсходовал 15.6 мс CPU. Все они пришлись на момент обнаружения выключения; в установившемся режиме прирост нулевой. Неудачный DDC-запрос возвращается мгновенно и процессор не занимает, потому что вызов блокируется на ожидании шины.

**Экономия вызовов.** Пока ОС сама сообщает, что экран погашен (`display_sleeping`) или мониторов нет (`monitors_disconnected`), опрос приостанавливается: в этом случае он ничего не добавит. При топологии, изменившейся по `WM_DISPLAYCHANGE`, handles мониторов пересоздаются, чтобы не застрять на устаревших.

## 5. Логика состояний

### Модель флагов
```rust
struct State {
    display_sleeping: bool,      // экран погашен: таймаут, кнопка монитора, сон системы
    session_locked: bool,        // сеанс заблокирован (Win+L) — только для журнала
    monitors_disconnected: bool, // SM_CMONITORS == 0
    monitor_unresponsive: bool   // монитор не отвечает по DDC/CI — выключен кнопкой
}

impl State {
    // Подсветка гасится ТОЛЬКО когда изображения на экранах нет.
    fn should_be_off(&self) -> bool {
        self.display_sleeping || self.monitors_disconnected || self.monitor_unresponsive
    }
}
```

### Почему блокировка сеанса не гасит подсветку
Требование изменилось по сравнению с первой версией ТЗ: утром при включении экрана комната ещё тёмная, и на экране ввода пароля подсветка нужна, чтобы набрать пароль. Поэтому `session_locked` намеренно **исключён** из `should_be_off()` и используется только для записей в журнале.

Практическое следствие: при `Win + L` не отправляется никакая команда — клавиатура продолжает светиться. Гаснет она только вместе с изображением на экране.

### Таблица переходов:
- **`WM_POWERBROADCAST` (`PBT_POWERSETTINGCHANGE`)**:
  - `GUID_CONSOLE_DISPLAY_STATE` или `GUID_MONITOR_POWER_ON`, значение `0` (Off) $\to$ `display_sleeping = true`
  - те же GUID со значением `1` или `2` (On/Dim) $\to$ `display_sleeping = false`
  - `GUID_SESSION_DISPLAY_STATUS` **не влияет** на решение, только пишется в журнал
- **`WM_POWERBROADCAST` (`PBT_APMSUSPEND`)**:
  - `display_sleeping = true`
- **`WM_POWERBROADCAST` (`PBT_APMRESUME*`)**:
  - `display_sleeping = false`
- **`WM_DISPLAYCHANGE`**:
  - `monitors_disconnected = (GetSystemMetrics(SM_CMONITORS) == 0)`
- **`WM_WTSSESSION_CHANGE`**:
  - `WTS_SESSION_LOCK` (0x7) $\to$ `session_locked = true`, команды нет
  - `WTS_SESSION_UNLOCK` (0x8) $\to$ `session_locked = false`, команды нет
- **`WM_APP_DDC`** (собственное сообщение от потока опроса):
  - `wparam == 0` $\to$ `monitor_unresponsive = true`
  - `wparam != 0` $\to$ `monitor_unresponsive = false`
- **Пробуждение экрана** (`PBT_APMRESUMEAUTOMATIC`, событие питания со значением ≠ 0):
  - `display_sleeping = false` и `monitor_unresponsive = false` — прежний вывод DDC после
    паузы устарел, подсветка возвращается сразу, а ближайший опрос уточнит состояние

### Почему `GUID_SESSION_DISPLAY_STATUS` исключён
Он описывает доступность дисплея сеансу и может оставаться `1`, когда сам экран уже погашен. Если обрабатывать его наравне с остальными, состояние дёргается: экран выключен, но приходит `1` — и подсветка включается обратно. На практике это наблюдалось как серия «выключено/включено» в пределах одной секунды.

### Правило отправки команд в клавиатуру:
Команда отправляется **только при изменении результирующего значения** `should_be_off()`:
```rust
let was_off = state.should_be_off();
// ... применяем изменение одного из флагов ...
let is_off = state.should_be_off();

if !was_off && is_off {
    send_turn_off_lighting();
} else if was_off && !is_off {
    send_restore_lighting();
}
```

## 7. Критерии приёмки
1. Запуск бинарника: процесс появляется в Диспетчере задач, консольное окно не появляется.
2. Простой: CPU = **0.00%**.
3. Тест блокировки (`Win + L`): подсветка **продолжает светиться** — она нужна для ввода пароля. Команда в клавиатуру не отправляется.
4. Разблокировка: подсветка остаётся в том же состоянии, ничего не меняется.
5. Выключение экранов (через таймер Windows): подсветка гаснет, при шевелении мышью / включении экрана возвращается.
6. Выключение монитора **физической кнопкой**: Windows не сообщает об этом, поэтому срабатывает опрос DDC/CI. Подсветка гаснет в пределах ~11 секунд после нажатия, после включения монитора возвращается.
7. Логирование: в файл рядом с exe записываются события из раздела 2, п. 6. Файл создаётся при первом запуске.
8. Single Instance: при повторном запуске второй процесс завершается сразу, первый продолжает работу.
9. Отключение клавиатуры по USB: ошибка HID не приводит к падению программы; при повторном подключении и следующем событии команды снова отправляются.

## 8. Проверка на устройстве и история правок протокола
1. **Формат пакетов и контрольная сумма**: проверены на реальном AK820 Wired. Первоначальное описание в этом ТЗ (65 байт, Report ID отдельно, команда в байте 1, сумма по байтам 1–62) было **неверным** и исправлено в разделе 3.2.
2. **Выключение подсветки**: первоначальная идея «пакет с `mode = 0`» не подтвердилась. Рабочий способ — запись конфига с байтом яркости `0x00` (раздел 3.3).
3. **Восстановление прежнего вида**: решено — конфиг из 29 байт снимается перед выключением и записывается обратно, поэтому режим, цвет и скорость сохраняются в точности.
4. **Скорость подключения**: замерено, что `HidApi::new()` занимает ~10 секунд, поэтому подключение перенесено на старт сервиса (раздел 3.4).
5. **Дублирующие GUID** `GUID_CONSOLE_DISPLAY_STATE` и `GUID_MONITOR_POWER_ON`: подписка на оба оставлена, конфликтов не выявлено.
6. **Блокировка сеанса (`Win + L`)**: сначала гасила подсветку, затем требование изменили — на экране ввода пароля подсветка нужна. Теперь блокировка не влияет на подсветку (раздел 5).
7. **Выключение экрана по таймауту**: проверено на реальной системе (таймаут монитора временно снижен до 1 минуты). Экран погас → `console_display_state = 0` → подсветка выключена; пробуждение → `console_display_state = 1` → подсветка восстановлена.
8. **Дребезг состояния**: наблюдался при широковещательной команде `SC_MONITORPOWER`, когда `GUID_SESSION_DISPLAY_STATUS` приходил со значением `1` при погашенном экране. Устранён исключением этого GUID из решения (раздел 5).
9. **Выключение монитора кнопкой**: проверено, что Windows об этом не сообщает вообще — ни `WM_DISPLAYCHANGE`, ни события питания, `SM_CMONITORS` не меняется. Добавлен опрос DDC/CI (раздел 4.3).
10. **Ложные отказы DDC/CI**: в замере на исправном мониторе одиночные отказы встречались в 6 случаях из 45 секунд. Поэтому решение принимается только после 4 неудачных попыток подряд.
11. **Стоимость опроса**: замерено — 15.6 мс CPU за 115 секунд, включая 90 секунд с выключенным монитором. В установившемся режиме прирост нулевой.

## 9. Память

Размер исполняемого файла (около 200 КБ) не определяет потребление памяти: процесс отображает в себя системные библиотеки (`SETUPAPI`, `user32`, `combase`, `ntdll` и другие), суммарный образ которых в этом случае — около 31 МБ.

**Рабочий набор** — это вся физически отображённая память процесса, включая **общие** страницы библиотек, которые уже находятся в памяти для других процессов. Поэтому именно он показывается в Диспетчере задач и именно он не является «своей» памятью приложения.

**Приватная память** — то, что принадлежит только этому процессу.

Достигнутые значения:

| Показатель | Было | Стало |
|---|---|---|
| Рабочий набор | 9.2 МБ | ~1.9 МБ |
| Приватная память | 2.38 МБ | ~2.4 МБ |

Приёмы, которые дали результат:

1. **Сжатие рабочего набора** (`SetProcessWorkingSetSizeEx` с `(SIZE_T)-1`) после инициализации и после каждой выполненной команды. Убирает из процесса страницы библиотек, к которым он больше не обращается. Память системы при этом не освобождается — страницы общие; при следующем обращении они подгружаются обратно. Это главный источник снижения видимой цифры.
2. **Стеки потоков** уменьшены с 2 МБ (умолчание Rust) до 128 КБ через `thread::Builder::stack_size`. Уменьшает резерв адресного пространства, а не резидентную память: стек занимает только реально использованные страницы.
3. **Освобождение списка HID-устройств**: `HidApi` держит перечисление всех HID-устройств системы, `HidDevice` от него не зависит, поэтому после открытия клавиатуры `HidApi` освобождается.

Профиль сборки уже включает `panic = "abort"`, `lto = true`, `opt-level = "s"`, `strip = true`.

Приватные 2.4 МБ — это в основном отображённые библиотеки и куча; ниже без отказа от HID-перечисления и окна сообщений не опуститься.

**Внедрённые библиотеки.** Если сторонняя программа (например, RivaTuner / MSI Afterburner, `RTSSHooks64.dll`) внедряется в процесс, она добавляет к рабочему набору свои мегабайты и к коду приложения отношения не имеет. Приложение можно добавить в исключения такой программы.
